# 第十四章 安全限额与剩余空间

## 14.1 为什么要有限额

压缩包可以在很小体积里声明极大的解压后大小。一个几百 KB 的文件解开后可能有好几
GB，这类东西俗称压缩炸弹。如果放任不管，一次误操作就能把设备的存储塞满，甚至让
系统因为写不下日志与缓存而崩溃。

因此本软件在解压前会先读一遍压缩包的条目表，把规模量出来，与设定的上限比对，
超限的直接放弃，一个字节都不写。

## 14.2 四道限额

「设置」页「炸弹防护」一组里有四项可调的阈值：

| 项目 | 含义 | 标准档默认值 |
| 条目数上限 | 单个压缩包解出的文件数上限 | 200,000 条 |
| 单文件上限 | 单个解压文件的大小上限 | 8 GB |
| 解压总量上限 | 单个压缩包解压后的总量上限 | 64 GB |
| 压缩比上限 | 解压后大小与压缩包大小的比值上限 | 1000 : 1 |

四条各自挡住一种形态：条目数挡的是「几百万个空条目」这种灌水，单文件上限挡的是
「一个文件就声明成几十 GB」，总量上限兜底，压缩比挡的是「小得离谱却撑得极大」。

前三条是精确的，不会误伤 —— 它们比的是归档自己声明的数字，而解压时还会逐条按
声明校验，对不上就报错。第四条是启发式的，因此另配了一道「地板」：只有解压后的
总量本身已经超过 1 GB 时才开始看比值。

那道地板是有实际意义的：一个 200 KB 压成 300 MB 的包，比值 1500 比 1 也照样无害
（最多写 300 MB），而不到 1 GB 的东西本来就不构成「撑爆磁盘」的威胁。地板把误伤
面收窄到「又大又空」这一种形态，那基本就是炸弹了。

## 14.3 三个预设档位

「解压上限」一行右侧的档位标签可以在三档之间循环切换：

| 档位 | 条目数 | 单文件 | 总量 | 压缩比 |
| 宽松 | 1,000,000 | 64 GB | 512 GB | 5000 : 1 |
| 标准 | 200,000 | 8 GB | 64 GB | 1000 : 1 |
| 严格 | 20,000 | 1 GB | 8 GB | 200 : 1 |

标准档是出厂默认。手机存储通常几十到上百 GB，一个包要写 8 GB 已经值得问一句了，
所以严格档是为手机准备的尺子；宽松档几乎什么都不拦，它是给「我很清楚自己在做
什么」的人准备的，不是给「安全」准备的。

在任意档位下，四项数值都会列在档位标签下面，只是不可点击 —— 选档位之前能先看到
数字，不用凭档名猜。

## 14.4 自定义档位

把档位切到第四次，标签显示「自定义」，此时四项数值变为可点击，逐项点开可以输入
新值。从任意预设档切入自定义时，会保留该档当前的数值作为起点，是从这一档微调
出去的，不用从零开始填。

## 14.5 剩余空间检查

上面四条比的都是**归档自己声明**的大小，而声明可以低报，嵌套还能把「一个包太大」
变成「N 个包各自都不大」。真正不受估算影响的判据只有一个：目标卷此刻还剩多少
字节。

因此本软件在每个压缩包开始解压之前，都会量一次目标卷的剩余空间，并与这个包声明
的解压后总量比对。判定时会留 64 MB 的余量 —— 把卷写到一格不剩会把整台机器拖垮，
而且解压本身也要临时空间。

判据写清楚是「解压后需要 12 GB，设备仅剩 3.2 GB，空间不足，已放弃」。

量不到剩余空间的情况（路径不可达等）会**跳过**这一条检查，而不是按 0 处理。量不
出来的东西不能拿来当判据。

## 14.6 被拦下时会怎样

被限额或空间检查拦下时，如果「错误时暂停」开着，会弹出弹窗说明原因，两个按钮是
「跳过」与「停止」；如果关着，直接记一条日志继续。日志上挂的标记分别是「炸弹
防护」与「空间不足」，状态是失败。

## 14.7 一处刻意的顺序

限额检查排在创建输出目录**之前**。也就是说，被拦下的压缩包连一个空目录都不会在
磁盘上留下。

# 第十五章 日志

## 15.1 记录什么

日志页按时间倒序显示历史记录。**每一次扫描与每一个被处理过的压缩包各记一条**。

每条日志包含：

| 字段 | 内容 |
| 标题 | 压缩包文件名；扫描记录写成「目录名（扫描）」 |
| 状态 | 成功、失败、跳过、部分之一 |
| 大小 | 压缩包本身的大小；扫描记录是本批各包之和 |
| 时间 | 发生的时刻 |
| 耗时 | 处理用了多久 |
| 标记 | 若干个短标签，说明这次发生了什么 |

## 15.2 标记的含义

| 标记 | 含义 |
| 分片 ×N | 这是一个 N 片的分卷包 |
| 嵌套 | 这个包是从别的包里解出来的 |
| 加密 | 这个包有密码 |
| 密码库 | 用密码库里的密码解开的 |
| 手输密码 | 用手动输入的密码解开的 |
| 伪后缀 | 后缀与实际格式不符 |
| N 项 | 解出了 N 个条目 |
| 炸弹防护 | 规模超限，主动放弃 |
| 空间不足 | 目标卷装不下 |
| 密码未匹配 | 确定是密码不对 |
| 密码或损坏 | 分不清是密码错还是数据坏 |
| 解压失败 | 压缩包损坏或其它错误 |
| N 个压缩包 | 扫描记录发现的数量 |
| 忽略 N 个容器 | 扫描时跳过的容器格式文件数 |
| N 个不可读 | 扫描时读不了的文件数 |

「加密」与「密码库」「手输密码」是两件事，会分开记。「加密」说的是这个包锁着，
后两者说的是钥匙是从哪来的。它们会分家：分卷加密包在扫描期认不出「加密」，
但它照样要密码才解得开，只看角标那一格会发现日志里一个密码相关的字都没有。

## 15.3 筛选

日志页顶部有一排筛选芯片：全部、成功、失败、跳过、部分。点击即切换。

筛选生效时，列表上方那一行会写成「筛出 X / 共 Y 条」两个数字。只报筛出来的条数
会让人以为被筛掉的记录没了，而右边那颗清空按钮删的偏偏是全部，所以两个数都要给。

筛选之后一条记录都没有时，空态显示的是「该分类下暂无记录」并提示切换到「全部」，
而不是「暂无记录」—— 后者与头部那行计数放在一起看，像是日志被谁弄丢了。

## 15.4 条数与清空

筛选条下面那一行左边显示当前条数，右边是「清空」按钮。

「日志保留条数」的设置项决定最多留多少条。超出之后每新增一条就丢弃最早的一条。
调小这个数字会立即生效，多出来的旧记录当场被丢弃。

清空按钮会删除**全部**记录，不只是当前筛出来的那些。因此点击后先弹确认卡片，
卡片上写明确切的条数。一条记录都没有时，清空按钮是灰色不可点的 —— 接了点击却
什么都不发生，比不接更让人困惑。

## 15.5 日志保存的位置与隐私

日志保存在应用私有目录下的一个 JSON 文件中，随应用卸载一起删除。

日志里**不记录完整路径**，只记录压缩包的文件名。这是有意的：日志文件是明文的，
完整的路径会暴露用户的目录结构与习惯。

日志里也**不记录密码**，只记录密码的来源。

# 第十六章 设置

## 16.1 设置的分类

设置页的内容分为六组，顺序为：递归与目录、智能识别、错误处理、炸弹防护、日志、
支持的格式，最后是「关于」入口。

## 16.2 递归与目录

**自定义输出目录**（默认关闭）

打开后，每次点「开始解压」会先让您选一个输出根目录，解压结果按源目录结构镜像
写进去。关闭则解到每个压缩包旁边。

这一项的详细行为见第九章。

**最大递归深度**（默认 20）

每进一层子目录、每解一层嵌套包各算一层。取值为 0 到 64，0 表示不递归。点击右侧
数值可以修改。详见第八章。

## 16.3 智能识别

**伪后缀时暂停**（默认开启）

检测到文件后缀与实际格式不符时，先弹出提示卡片让您确认。关闭则直接按识别出来的
真实格式解压，不再询问。

**无法解密时弹窗**（默认开启）

遇到加密压缩包时，无论这颗开关是开是关，本软件都会先用密码库里的密码自动尝试。
这颗开关决定的是**试完之后**：打开则弹窗询问，关闭则直接跳过该文件并记一条日志。

**手输密码存入密码库**（默认开启）

手动输入并且验证通过的密码，自动存进密码库，供以后自动尝试。关闭后手输的密码
只用于这一次。

默认打开的理由是：用户肯去手敲一个密码，本身多半说明这个包他还要再解（同一批
备份切出来的一组包、下次还会拿到的存档），敲完就丢等于让他重敲。想「这次只是
临时看一眼」的人可以关掉。

## 16.4 错误处理

**错误时暂停**（默认开启）

无法解压时弹窗询问，不自动跳过。关闭后自动决断并继续，只有权限问题仍然弹窗。

详见表见 13.3 节。

## 16.5 炸弹防护

**解压上限**

一个档位标签加四项数值。档位在宽松、标准、严格之间循环，第四次切到「自定义」，
此时四项数值变为可点击。

详见第十四章。

## 16.6 日志

**日志保留条数**（默认 300）

超出后丢弃最早的记录。取值范围 1 到 5000，点击右侧数值修改。调小立即生效。

下界取 1 而不是 0，是因为 0 是另一个语义（「不记录日志」），那应该是一个独立的
开关；一个能填 0 的条数框会把「我不想留历史」和「我填错了」混成同一种表现。

5000 条约合 400 KB，启动时读一遍毫无压力。

## 16.7 关于

「关于 DeepUnzip」一行进入关于页，那里有版本号、隐私说明、第三方组件清单与许可
全文。开源许可的全文只能从这个入口到达，因此这一行不只是「看一眼版本」。

## 16.8 设置的保存

所有设置项在改动后立即生效并同步保存，不需要「应用」按钮。

设置保存在应用私有目录中。开关类设置以独立的键保存；数值类设置（深度、日志条
数、限额）另有取值范围校验，从磁盘上读到超出范围的值时会夹回最近的合法边界。

## 16.9 设置在什么时候被读取

设置不是每一步都现查的，它在两个时刻被读取：

一、**界面显示时**。设置页上的每一行读的都是当前值，所以改完立刻能看到效果。

二、**一批开始解压时**。这一批会用一份当时拍下来的快照，整批都按这份快照走。

第二条是刻意的：如果解压跑到一半改设置，同一批里的包就会被两套规则处理，
日志看起来会自相矛盾。拍快照之后，改动的生效边界很清楚 —— 从下一批起。

日志保留条数是个例外，它不属于解压规则，改动立即生效，超出的旧记录当场被丢弃。

## 14.8 四条限额的判定顺序

限额不是随便排的，判定的先后影响报出来的原因是哪一条：

| 顺序 | 判据 | 记的标记 |
| 一 | 条目数 | 炸弹防护 |
| 二 | 单文件大小 | 炸弹防护 |
| 三 | 解压后总量 | 炸弹防护 |
| 四 | 目标卷剩余空间 | 空间不足 |
| 五 | 压缩比 | 炸弹防护 |

压缩比排在最后，是因为它前面有一道 1 GB 的地板：只有总量已经超过 1 GB 才看
比值。排在最后意味着一个同时超了总量又超了比值的包，报的是「总量超限」——
这句话更准确，也更好理解。

空间检查排在压比之前，是因为它是唯一用真实数字做的判断：前三条比的是归档自己
声明的大小，压缩比比的是两个声明值之间的比例，只有空间是量出来的。

## 14.9 嵌套与限额的关系

限额是**逐个包**判的，不是按整批累加的。一批里十个包、每个都刚好在限额之下，
合起来超过了限额总量，本软件会照解不误。

这是有意的：批的规模由用户自己选，十个包是用户选的，不该由软件替他决定「太
多了」。而单个包声明得过大不是用户能看出来的，那才需要拦。

空间检查是个例外，它天然是全局的：每解一个包，目标卷剩下的空间就在变少，下一
个包判的是新的剩余量。所以把大批量的包解到同一个卷上时，后面几个有可能因为
「空间不足」被拦下 —— 而前面几个已经成功了。

## 14.10 收紧限额之后

把档位从「标准」切到「严格」，或者自己填一组更小的数，只影响之后开始的批次，
已经在解的那一批不受影响。

被拦下来过的包在日志里留了记录，调宽限额之后重新跑，它们会重新被处理。日志不
会去改旧记录，所以你会同时看到一条旧的「炸弹防护」和一条新的「成功」—— 这两条
都是真的，各自说的是当时那一次的结论。
